B3PoW-Scratch live demo

Six small interactive pieces that show what B3PoW-Scratch actually does: a step-through of one BLAKE3 round, a visual sketch of the scratchpad mutation loop, a live mini-feed of the b3chain testnet, a real in-browser hash that matches the C++ consensus validator byte-for-byte, and a couple of helpers (faucet, wallet config) for actually trying the chain. Nothing on this page promises anything about price, hashrate, or production readiness; this is for understanding, not security.

PoW: B3PoW-Scratch v1.1 Spec: SPEC.md Reference: b3pow_ref.py Testnet: testnet.html
What this is and isn't. Components 1, 2, and 4 run on your machine and are useful for explaining the algorithm. Component 3 is a passive read of the public testnet. Components 5 and 6 are light convenience wrappers around services that already exist (faucet, wallet) — the wallet config in particular is a documentation blob, not a one-click integration; see its inline notes.

1. BLAKE3 round, step by step #

Why this matters. Every operation in B3PoW-Scratch is a BLAKE3 round (full inside the scratchpad init and the final hash, reduced to 2 rounds inside the mix step). One round is 8 quarter-round G(...) calls applied to a 16-word state: first 4 columns, then 4 diagonals. After 7 rounds the state is finalised. The cells of the state matrix below light up the moment a G(...) touches them, so the diffusion pattern (how a change in one cell spreads to all 16) is visible by eye.

2. Scratchpad mutation loop #

Why this matters. B3PoW-Scratch's GPU-hostility comes from 8 lanes hammering 8 read-modify-write cursors against a 1 MiB on-chip scratchpad in parallel. Below is one row per lane (8 rows), 256 cells per row (each cell = 512 B = 8 BLAKE3 blocks). The blue cursors hop to data-dependent addresses; the orange flash marks a write. This is a visualisation only: real B3PoW hashes mutate ~104 cells per millisecond, which at honest speed would just be a uniformly-flashing grid. See SPEC §6.3 (addressing), §6.4 (read), §6.6 (write).

Reference: SPEC §6.3–§6.6

4. Hash one header in your browser #

Why this matters. This is real B3PoW-Scratch, byte-identical to the C++ validator in b3chaind and the RTL on the FPGA mining card. It hashes a canonical header from the consensus vectors (src/test/data/b3pow_consensus_vectors.json) and compares against the expected output. First click takes a few seconds (1 MiB BLAKE3-XOF scratchpad warm-up); subsequent clicks on the same prev_hash reuse the pad. The compute runs in a Web Worker so the page stays responsive. 5. Request test coins #

Why this matters. The faucet at faucet.b3chain.org hands out 0.5 tB3C per request with a 24 h cooldown per IP and per address. This form validates the bech32 prefix client-side and opens the faucet page in a new tab pre-filled with your address. A JSON-API endpoint that would let us post the request and surface the txid here is on the roadmap; until then the actual request happens on the faucet site, and the "watch funds arrive" widget just links you to the explorer.

6. Wallet config #

Why this matters. Off-the-shelf wallets (Sparrow, Specter, Electrum) don't yet know about b3chain testnet because we haven't upstreamed the network metadata. This page provides a JSON "wallet-config blob" with all the parameters a user needs to plug in manually (network name, magic bytes, ports, address format, bech32 HRP, BIP44 coin type, electrum/RPC endpoints) and a BIP21 b3chain: URI that any registered handler will receive. Read the JSON for known limitations — the public electrum server is not deployed yet, so for now wallet operations work via a self-run b3chaind -chain=test node and the reference CLI.
